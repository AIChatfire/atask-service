# ADR-012: 用户回调地址的准入与投递——body 字段、fail-closed 白名单、只推终态

**Status**: Accepted (2026-09-13)
**Related**: 本仓库 ADR-010（受理链路、单一终态收口点、已知限制）、
本仓库 ADR-011（受理链路校验段纪律、用户回调由 `X-Callback-Url` 驱动）
**跨仓库参照**: stask-service 的回调设计（同为头驱动）；
上游口径参照火山方舟 Seedance「创建视频生成任务」的 `callback_url` 字段

## Background

### 触发这件事的两个事实

1. **客户按上游 API 文档传地址**。火山方舟 Seedance 的任务 API 把回调地址定义为
   **请求体顶层字段** `callback_url`，语义是「任务有状态变化时向该地址推送 POST，
   请求内容结构与查询任务 API 的返回体一致」。按该文档实现的客户端不会带
   `X-Callback-Url` 头。

2. **原实现只认头，且明确不读 body**。受理链路只取 `X-Callback-Url` 头，body 逐字节
   原样转发、网关不解析其语义（当时登记为契约的已知限制 L-5）。两条合起来的后果是
   **回调静默不发生**——客户端拿到 `202` 后按文档等一个永不到达的通知，网关侧也没有
   任何告警。这是最坏的失败形态：没有报错，只有沉默。

### 另一个独立的问题：回调目标是用户可控的出站地址

回调由网关**主动发起出站请求**，而地址完全由调用方提供。原实现对它零校验——这等于
给互联网开一个 SSRF 跳板：把地址填成内网服务或云元数据端点（`169.254.169.254`），
网关就会在任务终态时替攻击者发一次内网请求。

上游地址（`X-Upstream-Base-Url`）有 `UPSTREAM_ALLOWLIST` fail-closed 把关，而回调地址
当时是裸的——**同一个安全面上两条不对称的纪律**。

## Decision

### 1. 取值：头优先，body 顶层字段兜底

    生效地址 = X-Callback-Url 头（非空白）? 该头 : body 顶层 callback_url

- **头优先**：头是网关专有契约、语义明确，且存量客户端已在用；body 字段是兼容上游
  文档的**等价通道**，不是替代品。
- 头为空白串时按缺失处理（回退 body）——与 `upstream_addr.resolve_upstream_base`
  同一形态。
- **两者都无 → 不落键、不投递**。不给地址是正常请求，不是错误。
- 只在 `content-type` 含 `json` 且 body 是顶层对象时做浅解析；解析失败按「没给」处理，
  绝不因为一个可选增强让请求失败（与 `relayflow._extract_model` 同一宽容策略）。

### 2. 准入：四道防线，失败方向恒为拒绝

`app/services/callback_addr.py::assert_callback_allowed`（与 `upstream_addr.py` 同构）：

1. 仅 `http` / `https`；
2. 拒 URL userinfo（`http://user@host` 形态，即主机名前带 `user:pass@` 前缀）；
3. **字面 IP 必须是全局可路由地址**（`ipaddress.is_global`）——私网、回环、链路本地
   （含云元数据段）、保留段**无条件拒绝，即使白名单显式列了它**；
4. host 必须命中 `CALLBACK_ALLOWLIST`（逗号分隔），**空白名单 = 全部拒绝**。

第 3 条是**与 `upstream_addr` 的唯一实质差别**，理由是目标面不对称：上游基址本就是
内网固定地址（它本来就在私网里），而用户回调按定义应当公网可达——放行内网地址没有
正当场景，而它恰是 SSRF 最有价值的目标。

### 3. 摘除：默认模式下把字段从转发体里删掉

默认「网关接管」模式（`CALLBACK_PASSTHROUGH_UPSTREAM=false`）下，网关既然要自己签名
投递，就必须**让上游也回调不了**——否则客户端会收到两份通知（其中一份没有网关签名），
且它的回调地址被额外暴露给上游。

代价必须写清楚：**转发体不再逐字节同构**。摘除实现为「解析 → 删键 → dumps」，JSON
语义等价但键序/空白可能与客户端原文不同。三条约束把代价限住：

- **只在 body 顶层真的有该键时才改写**（头传地址时完全不碰 body）；
- 重构体单独存 `data.submit_body`，`data.request_body` 仍是原文（排障与原文回放）；
- `relayflow.submit_queue_task` 转发时优先取 `submit_body`、缺键回退 `request_body`，
  所以**绝大多数请求的转发路径一个字节都没变**。

### 4. 透传模式：取值与校验一起跳过

`CALLBACK_PASSTHROUGH_UPSTREAM=true` 时网关不摘除、不投递，地址只是转发给上游的普通
字段。此时**必须同时跳过取值与校验**：网关既然不投递，就**没有立场**判定该地址可信；
用白名单拦住一个上游本来接受的地址，会把「透传」做成半透传——客户端按上游文档写的
请求被网关 `400` 打回，而它完全无从得知原因。

该模式存在的前提是**上游自身实现了回调语义**。「上游是否支持」无法运行时探测，只能由
接入方声明，所以它是一个显式开关而不是自动判据。

### 5. 只推终态，不推中间态

火山方舟作为任务**执行者**，能在 `queued` / `running` 每次跃迁时推送。本网关是**中继**：
只在客户端轮询或后台 sweep 真正访问上游时才观测状态——**观测是抽样，不是事件流**。

据此推中间态会有三个后果：快速跃迁（`queued→running→succeeded`）必然漏报；通知乱序；
「恰好一次」无法保证（探测是重复执行的，而终态有 CAS 保证）。

因此**只推终态**。与火山的差异写进对接文档（`docs/CALLBACK-CONTRACT.md` §10）并给出
客户端应对：保留轮询兜底、不要用第一条通知启动进度展示。

### 6. 校验必须在任何副作用之前

与 body 上限（`413`）、分批头校验同一条纪律：非法地址返回 `400` 且**不留痕**——不落库、
不占并发槽、不占幂等键。放在占槽之后会让被拒的请求泄漏一个并发槽；放在落库之后会留下
一条永不提交的任务行（客户端拿着 `202` 一路轮询到超时）。

幂等占位确实已在此前发生，但受理链路的 `except` 分支会 `idem.release` 回滚它。回归锁：
`tests/test_callback_route.py::test_illegal_callback_url_is_400_without_any_trace`
（它同时断言同键换个合法地址仍能受理，即占位确实被回滚）。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 只认 body 字段、去掉头 | 头是网关专有契约且存量客户端在用；为对齐一个上游的口径而破坏自己的契约，方向反了 |
| 只认头、明确不支持 body（维持原状） | 客户按上游文档写的请求**静默失效**——没有告警、没有错误，是最坏的失败形态 |
| 提取但保留字段转发给上游 | 双投递：客户端收到两份通知，其中一份无签名；且回调地址被额外暴露给上游 |
| 解析域名后校验解析到的 IP | TOCTOU：校验时的解析结果与 `httpx` 出站时的解析结果不保证一致，只多一次 DNS 往返而不改变攻击面。信任边界交给白名单（只放行可信域名） |
| 白名单支持通配（如星号子域写法） | 一条配置放行一整个域，误配后果不可见；需要多子域就逐条列出 |
| 只在投递前（终态时）校验地址 | 坏地址要到任务跑完才暴露，客户端已经白等几分钟；且此时已落库、已占过槽 |
| 空白名单视为「放行全部」 | 与 `UPSTREAM_ALLOWLIST`、`ADMIN_TOKEN` 的 fail-closed 纪律冲突 |

## Consequences

- 客户按火山方舟 Seedance 文档写的请求**开箱可用**（body 顶层 `callback_url`），
  且不会被双投递。
- **部署前置**：新增 `CALLBACK_ALLOWLIST` 需配（不配 = 带回调地址的提交直接 `400`，
  但不影响不带回调地址的提交）。这是刻意的 fail-closed：回调目标是出站请求，
  默认开放等于默认暴露。
- 转发体在「body 带 `callback_url` 且网关接管」这一个组合下不再是逐字节同构，
  SPEC 的 L-5 已由「不做拦截」改写为「摘除后转发」。
- 回调仍**只推终态**：依赖 `queued` / `running` 通知的客户端需要改造。
- 变异测试自证了五处守卫会变红（去掉准入校验 / 去掉摘除 / 透传不跳过 / 去掉私网硬拒 /
  去掉空白名单分支），其中最后一条暴露了一条**假绿**——空 `allowlist` 会落到下一条
  host 分支、行为等价，只断言状态码抓不到差别，故补了一条断言错误文案的用例锁住
  「空白名单」这个诊断方向。

## 已知限制

1. **不防 DNS rebinding**：白名单配域名时，若该域名被解析到内网，本模块发现不了。
   理由见「被否决的替代方案」。
2. **主动取消（`DELETE`）不投递回调**：取消是客户端自己发起的，结果它已经知道。
   `relayflow.cancel_queue_task` 走独立的收敛路径（它多一步「尽力源头止损」，且必须
   发生在清令牌会话**之前**——那一步要用会话里的 sk 去发 `DELETE`），不复用
   `_finalize_queue`。**但取消同样是终态，收口动作一个都不能少**：2026-09-13 补齐了
   原先漏掉的 `tokensession.clear`（明文 sk 曾残留至 TTL 才被 Redis 回收）。回归锁见
   `tests/test_queue_route.py::test_cancel_clears_token_session_after_upstream_stop_loss`
   ——它同时断言「上游确实收到了那次 DELETE」，把清会话的**位置**一并钉住。
   **推论：以后给终态新增收口动作，必须同时问一句「取消路径要不要」。**
3. **会话过期后无 `expired` 通知**：本网关不设任务超时判死（本仓库 ADR-010 已知限制），
   因此不像火山那样推 `expired`。永久停在非终态的任务需要客户端 `DELETE` 或运维介入。
